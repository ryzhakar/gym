  concepts: borrow checker, unsafe, raw pointers, interior mutability, RefCell; domains_live: core; positions_seen: no-additional-borrow-checker-bypass (Rust lang team)

- Q: Should Rust let a method omit the `self.` prefix when calling another method or field on the same object, as some other languages allow, or keep the explicit `self.` requirement?
  concepts: method calls, field access, implicit self, readability; domains_live: core; positions_seen: keep-explicit-self (Rust lang team)
- Q: Should Rust allow programmers to define entirely new operator symbols, beyond overloading the fixed set of existing operators via traits like `Add`, to support building arbitrary domain-specific syntax?
  concepts: operator overloading, custom operators, DSLs, macros; domains_live: core; positions_seen: no-arbitrary-custom-operators (Rust lang team)
- Q: Should numeric overflow checking be enabled by default in release builds, trading performance for safety, or stay off by default in release as it is today with only debug builds checking?
  concepts: integer overflow, release vs. debug builds, performance vs. safety defaults, `Wrapping`; domains_live: core; positions_seen: keep-overflow-checks-off-in-release-open-to-change (Rust lang team)
- Q: Should Rust's type inference cross function boundaries, inferring parameter or return types from call sites, or stop at each function's signature as it does today?
  concepts: type inference, function signatures, local reasoning; domains_live: core; positions_seen: keep-function-boundary-inference-stop (Rust lang team)
- Q: Should Rust add mandatory, built-in garbage collection, requiring every target to support a GC runtime, or keep Rust runtime-free and, at most, support an optional/opt-in GC?
  concepts: garbage collection, language runtime, systems programming, opt-in vs. mandatory features; domains_live: core, embedded; positions_seen: no-mandatory-builtin-gc-open-to-optional (Rust lang team)
- Q: Should Rust add suffix conditional-modifier syntax (e.g. `return expr if condition;`, `break if condition;`), or require the existing explicit `if { return expr; }` form?
  concepts: control flow syntax, readability, evaluation order; domains_live: core; positions_seen: no-suffix-conditional-modifiers (Rust lang team)
- Q: Should Rust relax its guarantee that a type's size equals its array stride, to let types reuse trailing padding and reduce space at the cost of breaking existing pointer-arithmetic and unsafe-code assumptions, or keep the current size == stride guarantee?
  concepts: memory layout, padding, `size_of`, unsafe pointer arithmetic, ABI guarantees; domains_live: core, embedded; positions_seen: keep-size-equals-stride-guarantee (Rust lang team)
- Q: Should Rust let ordinary crate authors define new auto traits, given the semver-compatibility hazard this creates for every downstream type, or keep the ability to define new auto traits restricted?
  concepts: auto traits, OIBITs, semver hazards, negative impls; domains_live: core; positions_seen: unlikely-to-stabilize-new-auto-traits (Rust lang team, 2020); reconsidering-auto-trait-stabilization (Rust lang team, 2023)
- Q: When giving compiler-generated function/closure types without captured variables (upvars) new trait capabilities to enable safe trampolines, should the language implement the existing `Default` trait for them, or introduce a new, purpose-built trait instead?
  concepts: compiler-generated function types, `Default` trait, trampolines, FFI callbacks, trait design; domains_live: core; positions_seen: oppose-default-impl-prefer-purpose-built-trait (Mark-Simulacrum); implement-Default-for-no-upvar-closures (unattributed proposal discussed in the same note)
