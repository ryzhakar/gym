## f000256 — Rust and WebAssembly (undated — living document, unmaintained per its own banner; en)

### Questions

- Q: When a simulated grid must be conceptually infinite but memory is finite, how should the universe be bounded?
  concepts: state representation, memory bounds; domains_live: wasm; positions_seen: growable region (unbounded, risks OOM); fixed non-wrapping edges (kills edge-crossing patterns); fixed periodic/toroidal wrapping (chosen)

- Q: How should Rust expose computed state to JS across the wasm boundary — copy/serialize it, or share memory via pointer/opaque handle?
  concepts: FFI boundary design, wasm_bindgen, linear memory; domains_live: wasm, frontend; positions_seen: opaque handles + small copyable results (chosen general principle); return only changed deltas (named alternative, judged harder to implement); raw pointer + JS typed-array overlay (chosen concrete instance, replacing an initial Display→String copy)

- Q: Should per-cell state be stored one byte per cell or packed as bits?
  concepts: state representation, memory layout; domains_live: wasm; positions_seen: byte-per-cell (simple indexing, wastes memory); bit-packed FixedBitSet (memory-efficient, more complex indexing) — chosen as the refactor

- Q: Should a portable library perform its own I/O, or leave I/O to the caller and accept only in-memory data?
  concepts: sans-io design, portability across wasm/native; domains_live: wasm, core; positions_seen: perform I/O inside the library (implicit status quo, rejected); factor I/O out, take slices, let the caller do I/O (chosen)

- Q: Should a portable crate needing I/O expose synchronous or async I/O, and how should it abstract wasm vs native?
  concepts: async I/O, cross-target abstraction; domains_live: wasm, core; positions_seen: generic-over-Future async API (one named option); trait + per-target #[cfg] implementations (second named option); synchronous I/O (rejected — impossible on Web)

- Q: Should optimization effort be guided by profiling data or by the developer's hypothesis about where time/space goes?
  concepts: performance methodology; domains_live: wasm, core; positions_seen: profile first, let data override intuition (chosen, argued from two in-source cases where the hypothesis was wrong); optimize from hypothesis alone (implicitly rejected)

- Q: When debugging or benchmarking Rust destined for wasm, should the issue be reproduced as a native #[test]/#[bench] under OS-native tooling, or debugged directly on the wasm/Web target?
  concepts: debugging workflow, tooling maturity; domains_live: wasm; positions_seen: reproduce natively when the bug doesn't involve JS/Web APIs (chosen, with the caveat of first confirming the bottleneck is actually in wasm); debug directly on the wasm/Web target (kept only for JS-interaction-specific issues)

- Q: For code-size-sensitive wasm builds, should generic type-parameterized functions or trait objects be used?
  concepts: monomorphization, dynamic dispatch, code size; domains_live: wasm, core; positions_seen: trait objects — one function body, dynamic dispatch (chosen for size); generics — per-type copies, better optimization/inlining (named alternative, rejected on size grounds)

- Q: For size-optimized release builds, can opt-level="z" be assumed to beat opt-level="s", or must it be measured?
  concepts: compiler optimization flags, code size; domains_live: wasm; positions_seen: never assume, measure both (chosen); assume the more aggressive size flag always wins (rejected as unsafe assumption)

- Q: Should a wasm target keep the default (dlmalloc-derived) global allocator or switch to a smaller, slower one?
  concepts: allocator choice, code size vs speed; domains_live: wasm; positions_seen: switch to wee_alloc or avoid dynamic allocation entirely when size matters more than allocation speed (chosen); keep the default allocator (implicit status quo, faster but ~10KB heavier)

- Q: When a value is statically safe to unwrap but the compiler can't prove it, should code use a safe abort-based helper or an unsafe unchecked unwrap?
  concepts: panic elimination, undefined behavior, code size; domains_live: wasm, core; positions_seen: safe process::abort-based wrapper (default-recommended); unsafe unchecked_unwrap, only when "110%" certain and kept checked in debug builds (conditionally endorsed, named as the riskier alternative)

- Q: Should release builds enable LTO given its compile-time cost?
  concepts: link-time optimization, build configuration; domains_live: wasm; positions_seen: enable LTO — smaller and faster at runtime, worth the slower compile (chosen); skip LTO to keep compiles fast (named alternative, implicitly rejected)
