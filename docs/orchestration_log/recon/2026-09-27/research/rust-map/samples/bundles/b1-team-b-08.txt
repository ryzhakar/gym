Implement `wait_for_done` for `DpiTransfer`

---

@EliteTK · 2025-01-03T19:00:06Z:
## Motivations

`I8080Transfer` has this facility already, so this would introduce parity.

In general it can be useful when animating content on a display to avoid re-drawing more often than is necessary to ensure a smooth animation.

## Solution

An async `wait_for_done` function on the `DpiTransfer` in the same style as the one on `I8080Transfer`.

## Alternatives

I think it should be possible to achieve the same effect by simply implementing an appropriate `DmaTxBuffer` which tracks how much data has been transferred and synchronizes rendering to which frame is currently being requested combined with using `Dpi::send` with `next_frame_en` as `true`. But I think both styles would be appropriate to support.

## Additional context

I've discussed this with @Dominaezzz on matrix (in the Embassy channel) and he recommended I submit this feature request.

I have looked into this and may consider contributing this but please don't hold your breath as I think the `DmaTxBuffer` route would personally be preferable at the moment.

You can use the DMA to check if a frames worth of data has been sent. You'll have to use the PAC for this as the drivers don't expose this yet. 

In my own projects however, I avoid restarting transfers and I always use an infinite DMA buffer. By default every frame buffer in my project has it's last DMA descriptor pointing to it's first DMA descriptor, so the hardware just sends the frame over and over again automatically. When I want to switch frame buffers, I change the current frame buffer's last DMA descriptor to point the first DMA descriptor of the new frame buffer, and the hardware just "switches" automatically.
This generally works well until PSRAM is thrown into the mix and the bandwidth issues throws the data out of sync with the display signals.

@EliteTK · 2026-02-03T12:27:52Z:
Regarding why moving code to PSRAM should help:

The ESP32 has an MSPI peripheral which can be configured to expose SPI memory connected to SPI0/SPI1 (which incidentally share an SPI bus) to the cores as just normal memory (instead of your code having to manually use the SPI peripheral to load/store things). The normal program FLASH memory is accessed this way.

You can also access PSRAM through the MSPI peripheral.

Normally when you run code from FLASH, you use normal RAM, and you don't use SPI0/SPI1 for anything else, things work fine. But as soon as you access both FLASH and PSRAM then any read/write from/to PSRAM must wait for any outstanding FLASH read/write to complete first. This is just standard bus contention.

The DMA controller will try to stream the necessary data from PSRAM when it is needed, if it so happens that when DMA expects to read PSRAM that you were reading instructions from FLASH, this will delay the DMA controller's read, but the DMA controller doesn't expect to have to wait. Meaning that when the DPI peripheral starts sending out a signal, it might do so before the DMA peripheral has actually managed to get the data out of PSRAM. This causes your image to get out of synch.

If a read from flash can happen, it's very difficult to control when it will happen. As you noticed, calling a function in the wrong place can cause a flash read which would in turn stall the next DMA transfer. Or, at least, this is the hypothesis.

---

Now having written all that, I have to wonder why what I described can't also happen when you are only reading from PSRAM.

Because at the end of the day, PSRAM reads can be slow anyway. Which means that you could be starving the DMA peripheral even when you're reading from just PSRAM, as a PSRAM read of instructions from the wrong part of memory could still be happening when the DMA peripheral asks for pixels from PSRAM.

I will have to look into it, and it's entirely possible that I have made an error in my analysis above. I'd be happy to hear feedback.

But I think if you do bounce buffers backed with PSRAM, you can get the best of all worlds.

The way bounce buffers seem to be handled in e.g. LVGL is that you have two small buffers in RAM which get written to by LVGL directly and which are read from in a loop by the DMA controller. This is sub-optimal for various reasons, not least of all that you have to keep some kind of scene graph or data structure for your UI which you keep querying many times per refresh to render a sliver of screen.

But I don't see why you couldn't just set up DMA from two bounce buffers and then separately repopulate them from PSRAM (maybe even with more DMA).

The transfer into RAM can be started as soon as the current buffer has finished being read via DMA from the DPI peripheral. It needs to complete at any point between then and when that buffer is next needed, which should be more than enough time to avoid any problems with contention unless you're really pushing the chip to the limits.

As long as you accurately keep track of the correct offset into the real vbuffer, and you never somehow stall a DMA read from RAM, you should never have an issue. If a DMA read from PSRAM takes longer than needed, you can just cancel it and experience a small glitch, rather than a complete desync.

@Dominaezzz · 2026-02-03T13:08:59Z:
> Now having written all that, I have to wonder why what I described can't also happen when you are only reading from PSRAM.

So two things need the SPI bus. CPU and DMA.

If CPU accesses flash, the DMA has to wait until it can access PSRAM.

If CPU accesses PSRAM instead, the DMA and CPU share the PSRAM bandwidth 50/50 (this is not configurable). There's an arbitar that lets this happen.

So by moving code into PSRAM the DMA always has at least 50% of the bandwidth, as supposed to 0%.

@EliteTK · 2026-09-06T10:36:52Z:
@yanshay I've not had a chance to run your code yet, although I still might.

That being said, I've made major progress on my own project in this regard. I have 31.1 FPS full depth, full resolution, double-buffered glitch-free output without relying on XiP from PSRAM. But you do need to run the flash at 80MHz which probably won't work reliably without adjusting the timing[^psram-timing].

I allocate two framebuffers in PSRAM, I allocate two 1/16th bounce buffers in RAM. I set up a looping DMA transfer from the two bounce buffers to the LCD peripheral. The special trick I do is that I use 8x more descriptors than necessary, the descriptors alternate between the BBs. But by having descriptors which are in-sync with the screen, I can use the `DMA_OUT_CHx` interrupt to read ` OUT_EOF_DES_ADDR` which is enough information to figure out which exact screen slice just got emitted. This tells me exactly which portion of the current front buffer in PSRAM must be copied into the respective BB. I use Mem2Mem DMA to copy from PSRAM since doing it with the CPU is glacial (reads via cache, and then writes out via cache again) and ends up taking a huge chunk of the frame budget. If the Mem2Mem transfer is still running by the time the next BB must be refilled, I cancel it. Waiting at this point would likely just lead to cascading glitches. This happens very rarely.

Most importantly, even if PSRAM stalls, or you enter a long critical section (`esp-println`'s default features can cause this) then you won't get _persistent_ misalignment/glitches unless somehow the RAM -> LCD transfer stalls which I've not seen happen yet regardless of what has been going on.

The remaining obstacles are just how slow it is to write to PSRAM. A clear of a framebuffer takes milliseconds even with 64 byte cache lines, I am thinking I might use another M2M to do that, in order to avoid the cache and so I can do it eagerly after each frame. Double buffering eliminates screen tearing but complicates damage handling. Although there are plenty of optimisations left.

Either way, very promising.

@haricot · 2026-08-23T16:48:43Z:
Reopening this PR after rebuilding it from current main.

I tried to reduce the scope compared to the previous version. The old branch had BF16, FP8 and some other legacy CUDA changes mixed together, which made the PR harder to review.

This version only keeps the BF16 part for now.

I added an opt-in `cuda-legacy-bf16` feature. On sm_80+ the existing native BF16 path is unchanged. On older GPUs the compatibility code is only enabled when the feature is used.

I also changed the implementation quite a bit compared to the old branch. With recent CUDA 12.x, a lot of `__nv_bfloat16` conversions and basic arithmetic already work on older architectures, so instead of emulating everything I only added the few missing pieces Candle still needs, mainly BF16 `atomicAdd` and a few helper functions.

I tested this with CUDA 12.9 on a 1080 GPU.

Runtime tests currently pass for:

- casts and basic BF16 arithmetic
- min/max
- affine and unary ops
- reductions
- BF16 atomicAdd fallback
- BF16 matmul through the existing cuBLAS path with FP32 accumulation

I also checked the build with the feature disabled on sm_61, and with the feature enabled on sm_80.

I did not bring FP8 and the other changes from the previous branch back into this PR. I kept the old work in [bf16_candle_sav](https://github.com/haricot/candle/tree/bf16_candle_sav)   and, if useful, I can split the remaining parts into separate PRs later, for example:

- cuda: add opt-in FP8 storage compatibility for legacy GPUs
- cuDNN conv fallback when an architecture/operation is not supported
- pre-Volta MoE fallback 
- architecture-specific kernel/build selection
- tiled attention support, if it is still useful

Some of these parts may also need to be redesigned against current main rather than directly rebased.

Hopefully this version is easier to review than the previous one.

iroh 0.31.0 - Back At Fighting FitJanuary 15, 2025 by ramfox, matheus23
Welcome to a new release of iroh, a library for building on direct connections between devices, putting more control in the hands of your users.
For the holidays, we gifted you some regressions; in the new year, we fixed them 😅. We also refactored some code paths, added authentication to the relay servers, and made using relay-only mode for testing more programmatically sound!
🎉 Features!
🔰 Auth on relays!
This will be fun news for those of you who run your own relays! Not only do you have rate-limiting, but now you have tools to restrict access to your relays. Whether you are narrowing it down to your customers or your friends, or if you need to blacklist a bad actor, you can now restrict access to your relay server.
There is now a field access on iroh_relay::server::RelayConfig , that takes a fn you can supply. If it returns Access::Accept, the connection to the relay will be accepted, otherwise it will be rejected.
If you are just starting to spin up a project using iroh and don’t need a sophisticated function for allowing or denying connections, you can also provide an allowList or denyList list with your relay server configuration:
access.allowList = [
"NODEID1",
"NODEID2",
"NODEID3",
]
CopyCopied!
or
access.denyList = [
"NODEID1",
"NODEID2",
"NODEID3",
]
CopyCopied!
The default is everyone and parsing your toml config file will error if you include more than one of these options in it.
Check out PR #3086 for more information.
☎️ relay-only mode for testing!
The DEV_RELAY_ONLY compile time environment variable has been completely dropped and a PathSelection::RelayOnly option has been threaded through the entire stack when test-utils is enabled.
So, if you have test-util enabled, you can do the following to build an endpoint to force all data to be sent and received via the relay:
let endpoint = Endpoint::builder().path_selection(PathSelection::RelayOnly).bind().await?
CopyCopied!
We plan on improving this even more, so that it is easier to understand what might happen in your application if holepunching is unable to occur and all traffic is routed through the relay servers!
Checkout PR #3056 for more information.
🪲 Bug Fixes
😅 Connection Flop
If you noticed iroh’s connection establishment suddenly failed in some cases after version 0.30.0 you are not insane. We’ve fixed the bug and are back to our reliable connections in 0.31.0!
To understand the issue, you need some background information. Discovery in iroh relates a NodeId to (mainly) a relay url. We use that relay url to attempt to communicate with that NodeId and ask it about its direct addresses to holepunch with.
If you were not connected to a relay url, but did have a publicly available direct address you wanted to be discovered by, you could publish your direct addresses instead.
In a refactor, we accidentally combined the two, publishing both the relay url and any known direct addresses. Unfortunately, because our discovery system was designed to expect a single relay URL, rather than a whole list of records that also include direct addresses, what ended up happening was that we only parsed the first DNS entry for the record, essentially grabbing either the relay url or one direct address by chance, and discarding the rest. Because we did not have a relay url in many of these cases, we could not coordinate holepunching!
There’s a couple of things we’ve done to address this issue:
We rolled back the change to publish direct addresses in the PkarrPublisher: #3082
We’ve identified and fixed the bug that ignored all DNS record entries besides the first one: #3104
We’ve added better testing infrastructure to make sure we’ll identify these issues earlier the next time: #3121
💔 DNS / Pkarr segfault
If you have been using your own relay servers, you may have noticed some suspect behavior. Unfortunately, one of our DNS dependencies had an out-of-bounds parsing error. Some CPUs and OSs handled this error gracefully, others…did not. So if you were running this on a linux machine or on MacOS with an intel chip, you may have run across this. Good news is, the bug is fixed, the dependency released, and there are some nice fuzz tests ensuring it won’t happen again!
Checkout out this PR for more information.
🔒 Deadlock on the relay (not released)
We did a TON of work refactoring the iroh-relay story this release. One of those pieces was to refactor the server side of the connection to help simplify the code and not have so many layers between the connection and the structures the server uses to manage those connections. We did this by removing an unnecessary actor and using some higher-order data structures to ease some of the burden of reading through locks and mutexes. Unfortunately, we foot-gunned a bit there, and needed to do a follow up PR to un-footgun.
So, if you were following along on main, your iroh-relay server may have seen an hiccup in there. The issue was fixed and was never in a released version of the iroh-relay, so most of you will not even know what we are writing about here.
Checkout PR #3099 for more information.
