So, you have a bunch of kinds of peripherals you want to support. Each kind of peripheral has a crate that can be used to support it. You want to have a generic struct that has some common data fields and some peripheral-specific fields. Is this correct?
The way I'd do this is to create a new struct type for each kind of peripheral. Then, have a generic struct that contains these new structs. Something like this:
// Suppose that the kinds of peripherals are Foo and Bar.
struct FooData { .... }
struct BarData { .... }
trait PeripheralSpecificData { .... }
impl PeripheralSpecificData for FooData { .... }
impl PeripheralSpecificData for BarData { .... }
struct Peripheral<T> {
common_field_1: i32,
common_field_2: i32,
peripheral_specific: T
}
impl<T: PeripheralSpecificData> Peripheral<T> { .... }

@kpreid · 2024-08-11T14:14:42.779Z:
anichang:
error[E0592]: duplicate definitions with name new
What's wrong with that?
What's wrong, as far as the compiler is concerned, is that if a single type implemented both AdcBase and GpioBase, it would be unavoidably ambiguous which new() to call. The only way to have duplicate associated function names is to define them in a trait or traits, where the trait name and generic parameters can be used to disambiguate.
In the code you show, they are identical except for bounds, so you could just remove the bounds and have only one new(). If you need both to exist, give them two different names (perhaps starting with “from_”). If you need to call them from generic code, you need to make them a function of a single trait.

@kpreid · 2024-08-11T18:12:37.327Z:
anichang:
That stuff looks juicy: is it for introspection/reflection?
TypeId provides an opaque token which can be used to compare equality of concrete types. Any builds on TypeId to add dynamic-to-concrete downcasting support: if you have an &dyn Any, you can say “if this points to a String, give me a &String”.
You cannot downcast to a trait — in fact, you can almost never write any program that depends on answering the question “does this type implement this trait”, because that turns out to be hard to define in a way that gives a consistent answer (due to the possibility of generic bounds that depend on lifetimes, in particular).
Rust in general does not have general reflection / RTTI capabilities where you ask, at run time, what characteristics a type has. The typical substitute is derive macros, that look at the definition of a type at compile time and generate a trait implementation which exposes specific information about a type.
There are libraries that use traits and derive macros to build a more general reflection system, for types that opt in by implementing the trait — the one I have heard of is bevy_reflect, but I haven't used it myself.
anichang:
I need the adc.rs to be part of the general hal crate, to be built for different archs. And I need for the implementation to be in the atmega2560 lib in order to not include the arch-specific crates in the general hal crate. How do I solve this?
The answer to problems like this is always to use a trait. And in this case, in order to satisfy trait coherence, you'll also have to create at least one type that is defined in your atmega2560 lib — this is to avoid conflicts where crates C and D both impl crate_a::Trait for crate_b::Type.
I feel like I should note that I don't have any experience with Rust embedded HALs. I've been giving you general Rust advice, but there's a lot of prior work on designing HALs that I can't tell you about because I haven't worked in that space.

@Karsten · 2024-08-12T09:37:41.079Z:
For GPIO you should definitely use embedded-hal's traits InputPin and OutputPin. This is supported by all HALs, so if you write a function that depends on these traits it can be used with any HAL's GPIO pins like this:
fn blink<PIN: OutputPin, DELAY: DelayNs>(pin: &mut PIN, delay: &mut DELAY, on_time_ms: u32, off_time_ms: u32, times: usize) {
for _ in 0..times {
pin.set_high().unwrap();  // unwrap may be fine if an internal pin is used, because those are typically infallible anyway
delay.delay_ms(on_time_ms);
pin.set_low().unwrap();
delay.delay_ms(off_time_ms);
}
}
All HALs will have a way to get a pin object that implements OutputPin (and probably a way to get a DelayNs object in this case).
ADC is a little bit more complicated embedded-hal had an ADC trait in the past, but this was removed in version 1.0, because it turned out to be quite complicated to define a useful common trait that is versatile and can also be supported by most hardware. Maybe a consensus will be reached in the future, but for now I would recommend defining your own trait for your purposes like this for example:
trait AdcPin {
fn read(&mut self) -> Result<i16, AdcError>;
}
This trait would have to be implemented for each HAL that you want to support using their ADC implementation. See https://docs.rs/rp2040-hal/latest/rp2040_hal/adc/index.html and https://rahix.github.io/avr-hal/avr_hal_generic/adc/struct.Adc.html for examples of how HALs provide this functionality.
As a side note it does not work very well to think like you would in C or C++. Embedded Rust ist fundamentally different and it is very unlikely that you will succeed by trying to write C code in Rust. Read the Embedded Rust Book and similar to learn how things are done in Rust.

The idea behind the singletons is that each hardware peripheral is exactly once in the MCU physically. The singletons model that. That way you can't accidentally use them concurrently and cause race conditions. If you need to use them in multiple places you can by using a Mutex for example.
It seems you want to learn the hard way and that is fine. Just keep in mind that C and Rust are fundamentally different languages. In Rust the idea is that you have to prove to the compiler that you have thought of every edge case and potential concurrency problem, otherwise it won't compile whereas the C compiler has more of a YOLO approach and just trusts that you (hopefully) know what you are doing.
Writing unsafe Rust is way more complicated and potentially dangerous than writing C, because C is way more conservative about it's assumptions. You can very easily write code that breaks from one compile to the next or has hidden race conditions or breaks from one compiler version to the next.
If you don't care about the guarantees Rust can offer you are better of writing C, because unsafe Rust written by a non-expert is way more dangerous than C IMO.

The point of the peripherals singleton is that there's a fixed set of known peripherals in the hardware; by providing a singleton object that represents "all fixed hardware in this MCU", and requiring you to pass around references to hardware, you get the compiler to help you ensure that there's no surprise race conditions.
For example, if I write a function fn use_i2c<I2C>(controller: &mut I2C) where I2C: Deref<rp2040_pac::i2c0::RegisterBlock>, the compiler will now enforce, at compile time, that I'm given access to one of the 2 RP2040 I2C controllers (since they both implement Deref<rp2040_pac::i2c0::RegisterBlock>, as they're identical hardware at different addresses), and that I am the only entity with access assuming no buggy unsafe code (since I took &mut, which implies exclusive access).
I can extend this further if I'm using both cores; by making the where clause I2C: Deref<rp2040_pac::i2c0::RegisterBlock> + Send, I'm now telling the compiler to ensure that I can pass this I2C peripheral across to another thread running on another core.
This is a powerful use of the compiler's features - I now have a compile-time guarantee that if there's racy access to a peripheral, it must be a consequence of an unsafe block somewhere containing buggy code. I can then exploit this guarantee by minimising the size of unsafe blocks in my program, so that I can audit them all by hand and be confident that they don't race to access the peripherals, rather than being required to audit the entire program.

This is fixed by the hardware, and you cannot change it without stopping using the RP2040 IC, and switching to a different IC (such as the RP2350, or something from the STM32 family).
The point of modelling the hardware via a singleton representing "all the peripherals that are part of the RP2040 silicon" is that you get compiler assistance for getting things right; it doesn't have to be a perfect correspondence to your final board, but it forces you to go through one place (main!) to get at hardware, because it's otherwise impossible to access the peripherals safely.
You can, of course, use unsafe code to get access to a copy of the peripherals, but now you've lost the compiler's assistance in controlling your access to peripherals.
And, for example, a neopixel controller that relies on the PIO peripheral on the RP2040 to control it might take &mut impl Deref<Target=rp2040_pac::pio0::RegisterBlock> as its parameter type telling it where the controller is; you can get this by deconstructing a rp2040_pac::Peripherals and giving it either PIO0 or PIO1, and by taking it like this, you guarantee that the neopixel controller has exclusive access to the PIO block you've chosen for it - your code simply won't compile if you try to (e.g.) reuse the same PIO block for concurrent control of a neopixel and a DVI output, telling you early on that your code is wrong.

@kornel · 2025-12-22T12:57:29.576Z:
mod declares where a module exists, not that a file is a module.
Just like fn name or struct name makes the name exist where you wrote it, so does mod name make name exist where you wrote it.
Rust modules aren't files that say what they are. Rust defines named "items", and some of the items can be of a module type (other types are functions, structs, constants, static variables), and some of the modules can load their body from a file if needed.
#[path="/etc/passwd"]
mod name;
#[path="/etc/passwd"]
mod name2;
mod is discovered first, and then it looks for a file if needed. It's possible for the path to be anything. You can even make two different modules load the same file (it's not useful, but conceptually possible).

#include analogy will cause confusion, because include is similar only in superficial irrelevant way (loads a file), but very different and almost entirely opposite in every meaningful way.
The closest analogy that isn't wrong would be:
mod name {
#include "name.rs" // fictional syntax
}
so include isn't mod, because:
include is repeated every time the file is needed. mod for a file is used only once ever throughout the entire project.
include doesn't define anything. mod creates a named item.
include pollutes namespaces, mod creates isolation barrier.

@Tom47 · 2025-12-22T14:06:00.175Z:
In Rust, code organization is not based on files. And modules are not imported, they just are.
If Rust module system confuses you, I would suggest not to split your code in multiple files, but instead put everything into one file, like for example:
// main.rs
mod holder {
trait Holder {}
}
mod stack {
struct Stack {}
impl crate::holder::Holder for Stack {}
}
fn main() {}
or like this:
// main.rs
mod holder {
trait Holder {}
}
mod stack {
use crate::holder::Holder;
struct Stack {}
impl Holder for Stack {}
}
fn main() {}
or:
// main.rs
mod stack {
mod holder {
trait Holder {}
}
use holder::Holder;
struct Stack {}
impl Holder for Stack {}
}
fn main() {}
Experiment with various combination/organization of mods and uses.
And once you are familiar with how modules (all in one file) work, there is one final step:
Writing just
mod foo;  // no {} here
will make compiler look into a file named foo.rs or foo/mod.rs (or more deeply nested if you are inside another module) and treat its contents as if you had written:
mod foo {
// paste contents of the file here
}

if you want to measure "real world general performance", i.e. averaged performance under a broad variety of uses cases, without assumptions about how the hashtable is used, then here is a good way to do it:
generate random csv files which specify sequences of hashtable actions, i.e. "insert X Y", "delete X", "find X"
in each language, parse the table and apply the sequence of operations
benchmark the average performance across several different tables (for example, one table could be truly random data, another could consist of many writes followed by a few reads, or many reads followed by a few writes, then keep adding tables to your benchmark which you know are representative of real world cases).
This has an additional advantage - for any benchmark consisting of loops written in the source code, you have a chance that your compiler can optimize the loops somehow, even if you use blackbox judiciously. However, when you parse the operations from a file, this is impossible, since the program needs to execute arbitrary actions in arbitrary order.
fuji-184:
actually the Hashmap is slow, but because it is covered by high performance allocator it looks fast. While the other language Hashmap is actually fast but because it is used with low performance allocator it looks slow, that actually if all uses same component/allocator it is faster.
The way I have dealt with this in the past is to benchmark with a simple bump allocator which never releases memory. Then allocate a big chunk to your benchmark (outside of the timing loop of course) which you know is enough to hold the entire hashtable. This type of allocator is the cheapest possible one, it isn't practical for most real world cases, but, it should erase any differences caused by allocators in different languages. The fact that Go doesn't let you control the allocator would break this strategy, however, as a managed language, you should expect that go gives you much less control over many things.
However, if you're measuring "real world" performance, in the real world, most people just pick the default allocator used by their library. I see this as decent justification for including those differences in your benchmark.

Fachliche Typen
In langlebigen Softwareprojekten ist es ratsam, fachliche Typen unabhängig vom eingesetzten Framework zu definieren. Im Rahmen der in den vorherigen Teilen gezeigten E-Mail-App bietet sich zum Beispiel der Typ EmailAddress an: Dieser Typ kapselt die Validierung und Repräsentation einer E-Mail-Adresse und stellt sicher, dass nur gültige Werte im System verwendet werden. Die Logik zur Prüfung – etwa auf das Vorhandensein des Zeichens @ – ist direkt im Typ verankert und nicht Teil der Crux-App.
Dadurch bleibt die fachliche Logik klar von technischen Details getrennt. Sie kann unabhängig von Crux, anderen Frameworks oder der konkreten Plattform getestet, wiederverwendet und weiterentwickelt werden. Sollte sich die technische Umgebung ändern, bleibt die Kernlogik erhalten und muss nicht neu geschrieben werden.

Peertube
Fachliche Typen wie EmailAddress erhöhen die Wartbarkeit und Verständlichkeit des Codes und schützen vor Fehlern, indem sie ungültige Zustände bereits beim Erstellen verhindern.
Weiterlesen nach der Anzeige
Listing 1: Fachlicher Typ EmailAddress
#[derive(Clone, PartialEq, Eq, Hash, Debug, serde::Serialize, serde::Deserialize)]
pub struct EmailAddress(String);
#[derive(thiserror::Error, Debug)]
pub enum EmailError {
#[error("missing @")]
MissingAt,
}
impl EmailAddress {
/// Der Smart-Constructor garantiert eine gültige Adresse
pub fn parse(s: impl Into<String>) -> Result<Self, EmailError> {
let s = s.into();
if s.contains('@') { Ok(Self(s)) } else { Err(EmailError::MissingAt) }
}
pub fn as_str(&self) -> &str { &self.0 }
}
Fachliche Typen wie EmailAddress lassen sich unabhängig vom Framework testen.
Listing 2: Tests für EmailAddress
#[cfg(test)]
mod tests {
use super::*;
#[test]
fn valid_email_is_accepted() {
let email = EmailAddress::parse("marcel.koch@example.org");
assert!(email.is_ok());
assert_eq!(email.unwrap().as_str(), "marcel.koch@example.org");
}
#[test]
fn invalid_email_is_rejected() {
let email = EmailAddress::parse("marcel.kochexample.org");
assert!(email.is_err());
assert_eq!(email.unwrap_err(), EmailError::MissingAt);
}
}
Der erste Test prüft, dass eine gültige E-Mail-Adresse akzeptiert und korrekt gespeichert wird. Der zweite Test stellt sicher, dass eine ungültige E-Mail-Adresse (ohne @) abgelehnt und der passende Fehler (MissingAt) zurückgegeben wird.
Aufteilung in mehrere Apps oder Crates
Wächst das Entwicklungsteam der App, kann es sinnvoll sein, das Team und auch die Anwendung in mehrere eigenständige Apps und Crates aufzuteilen. Ein Kontaktmanagement könnte die bisherige E-Mail-App erweitern und alle eingehenden Kontaktdaten speichern, aktualisieren oder löschen. Dabei bekommt das Kontaktmanagement eine eigene Crux-App, verwaltet in einem separaten Crate. Dieses separate Crate beinhaltet ein abgegrenztes Feature und wird auch als Feature-Crate bezeichnet. Jedes Feature-Crate definiert dabei seine eigenen Events, Models, ViewModels und Effekte – das Model ist also explizit Teil des jeweiligen Features. Die Haupt-App integriert die einzelnen Feature-Crates und koordiniert deren Zusammenspiel.
Listing 3: contacts (Feature-Crate)
// contacts/src/lib.rs
#[derive(Clone, Debug)]
pub struct Contact {
pub name: String,
pub email: EmailAddress,
}
pub enum ContactsEvent {
AddContact(Contact),
RemoveContact(EmailAddress),
EditContact(EmailAddress, Contact),
}
#[derive(Default)]
pub struct ContactsModel {
pub contacts: Vec<Contact>,
}
pub struct ContactsViewModel {
pub contacts: Vec<Contact>,
}
pub enum ContactsEffect {
ShowContactAdded(EmailAddress),
ShowContactRemoved(EmailAddress),
}
pub fn update(event: ContactsEvent, model: &mut ContactsModel) -> Vec<ContactsEffect> {
match event {
ContactsEvent::AddContact(contact) => {
model.contacts.push(contact.clone());
vec![ContactsEffect::ShowContactAdded(contact.email)]
}
ContactsEvent::RemoveContact(email) => {
model.contacts.retain(|c| c.email != email);
vec![ContactsEffect::ShowContactRemoved(email)]
}
ContactsEvent::EditContact(email, new_contact) => {
if let Some(c) = model.contacts.iter_mut().find(|c| c.email == email) {
*c = new_contact.clone();
}
vec![]
}
}
}
pub fn view(model: &ContactsModel) -> ContactsViewModel {
ContactsViewModel {
contacts: model.contacts.clone(),
}
}

Die Haupt-App aggregiert die Feature-Modelle und koordiniert die Kommunikation:
Listing 5: Haupt-App-Integration (App-Crate)
// app/src/lib.rs
use contacts::{ContactsEvent, ContactsModel, ContactsViewModel, ContactsEffect};
use email::{EmailEvent, EmailModel, EmailViewModel, EmailEffect};
pub enum AppEvent {
Email(EmailEvent),
Contacts(ContactsEvent),
}
pub struct AppModel {
pub email: EmailModel,
pub contacts: ContactsModel,
}
pub struct AppViewModel {
pub email: EmailViewModel,
pub contacts: ContactsViewModel,
}
pub enum AppEffect {
Email(EmailEffect),
Contacts(ContactsEffect),
}
pub fn update(event: AppEvent, model: &mut AppModel) -> Vec<AppEffect> {
match event {
AppEvent::Email(email_event) => {
email::update(email_event, &mut model.email)
.into_iter().map(AppEffect::Email).collect()
}
AppEvent::Contacts(contacts_event) => {
contacts::update(contacts_event, &mut model.contacts)
.into_iter().map(AppEffect::Contacts).collect()
}
}
}
pub fn view(model: &AppModel) -> AppViewModel {
AppViewModel {
email: email::view(&model.email),
contacts: contacts::view(&model.contacts),
}
}
Durch diese Aufteilung bleibt die Anwendung modular, testbar und erweiterbar. Jedes Feature verwaltet seinen eigenen Zustand und lässt sich unabhängig entwickeln, testen und warten. Die Haupt-App sorgt für die Orchestrierung und das Zusammenführen der einzelnen ViewModels zu einer konsistenten Oberfläche. So entsteht eine skalierbare Architektur.
